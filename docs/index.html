01設計上の選択とアーキテクチャ

clasp CLI をラップしないという選択が、この Action の機能すべての前提になっている。代償として「clasp 互換を自前で保証する責任」を負い、それをゴールデンテストで担保する。

clasp push / clasp deploy を CI から呼ぶラッパーではなく、Apps Script API（projects.updateContent / projects.versions.create / projects.deployments）を直接呼び出す。既存の clasp ラッパー系 Action が対話プロンプトやエラー出力、バージョン間の仕様変更に振り回されるのは、CLI を外側から操作する構造そのものに原因がある。

その代わり .claspignore の解釈やファイル種別の判定といった互換性は自前の責任になる。これは実際の clasp status --json の判定結果と本実装の出力を突き合わせるゴールデンテストで担保している。

GitHub Actions への依存は deploy/ と rollback/ の薄いアダプタ層に閉じ込め、ロジックは packages/core に置く。HTTP は Node のネイティブ fetch のみを使い、googleapis SDK は使わない（呼ぶエンドポイントは6個だけであり、バンドルサイズと依存を減らす方が利益が大きい）。

最小の導入例

name: Deploy GAS
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: yut0takagi/gas-deploy-action/deploy@v0
        with:
          credentials: ${{ secrets.CLASPRC_JSON }}
          script-id: ${{ secrets.GAS_SCRIPT_ID }}
          root-dir: dist
          deployment-id: ${{ secrets.GAS_DEPLOYMENT_ID }}

root-dir にはビルド済み JS を指定する。TypeScript のトランスパイルは本 Action の責務ではない。バージョンは @v0.1.1 のように固定するか、@v0 でパッチリリースに追従させる。

02認証 — 最も壊れやすい箇所

この Action が「1週間後に壊れる」原因のほぼすべては OAuth 同意画面の状態にある。導入時に必ず確認すべき設定は、コードでも入力でもなく Google Cloud Console 側にある。

Apps Script API は Google 側の仕様としてサービスアカウントのトークンを受け付けない。したがってユーザーアカウントの refresh token を Secret に格納する方式が現状唯一の選択肢である。認証情報の用意には2つの経路があり、権限の広さが違う。

本 Action が絞っているのはアクセストークンのスコープであり、リフレッシュトークン自体の権限は狭まらない。経路 B では、Secrets に保存される refresh token は clasp が認可された時点の13スコープを持ち続ける。「本 Action は2スコープしか使わない」ことと「漏洩時の被害が2スコープ分に収まる」ことは別である。真の最小権限を得るには経路 A を使う。

表2: OAuth 同意画面の状態と refresh token の寿命
アカウント種別同意画面の設定refresh token の寿命症状
いずれもテスト（Testing）のまま7日初回成功の約1週間後に invalid_grant で停止する
Google Workspace内部（Internal）失効しない—
個人 Gmail本番（Production）に公開失効しない公開時の警告・確認の要否は未検証（10節）
いずれも再認証ポリシーが掛かったアカウント—invalid_grant / invalid_rapt。保存済みトークンでは突破できない

出所: README「OAuth 同意画面の状態を必ず確認する」。再認証ポリシー下のアカウントは無人 CI に向かないため、専用のデプロイ用アカウントを推奨する。

~/.clasprc.json は { tokens: { <アカウント名>: {...}, default: {...} } } の形で複数アカウントを保持できる。本 Action は常に default を使い、複数あって default が無い場合は黙って推測せずエラーにする。エラーメッセージ中のアカウント名は、メールアドレス形式であれば伏せる（CI ログに出るため）。

失効を先に検知する — token-check アクション

失効は「次にデプロイが必要になった瞬間に初めて気づく」形で現れる。障害対応でロールバックしようとしたら認証が通らない、が最悪の形である。token-check を週次 cron に置いて先に検知する。何も書き換えない — refresh token は失効しない限り不変で、更新する対象がそもそも存在しないためである（設計仕様 §7.1「更新ではなく死活監視」）。

このアクションはまだリリースされていない。v0.1.1 および v0 タグには含まれないため、下の例は次のリリース以降で動作する。それまでは @main を指定する。

on:
  schedule:
    - cron: '0 3 * * 1'     # 毎週月曜

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - id: check
        uses: yut0takagi/gas-deploy-action/token-check@v0
        with:
          credentials: ${{ secrets.CLASPRC_JSON }}
          script-id: ${{ secrets.GAS_SCRIPT_ID }}

      - name: 失効していたら Issue を起票する
        if: failure() && steps.check.outputs.status == 'invalid'
        run: gh issue create --title "GAS の認証情報が失効しました" --body "${{ steps.check.outputs.summary }}"
        env:
          GH_TOKEN: ${{ github.token }}

status意味既定の挙動該当する reason
valid使える何もしないok
invalid使えない。この状態のままではデプロイが失敗するジョブを失敗させるtoken-invalid / insufficient-scope / unauthorized / api-disabled / access-denied / not-found

出所: packages/core/src/token-health.ts、token-check/action.yml。分岐にはメッセージ本文ではなく reason を使う。

unknown で既定ではジョブを落とさない。ランナーが Google に到達できなかっただけで週次ジョブが赤くなると、本当に失効したときの赤が「またいつもの失敗」として埋もれる。監視の価値は赤が希少であることに依っている。到達性の問題まで検知したい場合は fail-on-unknown: true を指定する。

script-id を指定すると、トークンの交換に加えて実際にそのプロジェクトを読み取れるかまで確認する（project-checked 出力で確認範囲が分かる）。「トークンは生きているが Apps Script API を無効化された」「対象スクリプトの権限を外された」は交換だけでは検知できない。gasdeploy.yml の設定モードには対応しない — 死活監視が確認するのは認証情報そのものであって、デプロイ対象の一覧ではないためである。

04複数プロジェクト構成

1リポジトリに複数の GAS プロジェクトを置き、環境ごとにデプロイできる。逐次実行し最初の失敗で停止するが、全ターゲットの状態を必ず出力するため、赤いジョブを見た人が Apps Script のコンソールを開かずに現状を把握できる。

version: 1

defaults:
  ignore:
    - "**/*.test.js"
    - "node_modules/**"

projects:
  web-app:
    rootDir: apps/web-app/dist
    type: webapp
    environments:
      dev:
        scriptId: ${DEV_WEBAPP_SCRIPT_ID}
      prod:
        scriptId: ${PROD_WEBAPP_SCRIPT_ID}
        deploymentId: ${PROD_WEBAPP_DEPLOYMENT_ID}

  sheet-tools:
    rootDir: apps/sheet-tools/dist
    type: bound
    environments:
      prod:
        scriptId: ${SHEET_TOOLS_SCRIPT_ID}

${VAR} は GitHub Actions の式ではない。gasdeploy.yml はリポジトリ内のただの YAML なので ${{ }} は展開されない。本 Action が ${VAR} を環境変数から展開するため、ワークフローの env: で渡す。未定義の変数はエラーになる（空の scriptId で API を叩いて意味不明な 404 になるのを防ぐため）。

環境が無いプロジェクトの扱い

projects: all のとき、指定環境を持たないプロジェクトはスキップされる（prod しか持たないプロジェクトがあってよい）。一方 プロジェクト名を明示指定した場合は、環境が無ければエラーになる。名指しした対象がデプロイされないまま成功と表示されるのを防ぐためである。

05PR への差分コメント

dry-run と組み合わせると、マージ前に「何が本番に出るか」を PR 上で確認できる。コメントの失敗はデプロイの失敗にしない設計になっている。

permissions:
  contents: read
  pull-requests: write     # これが無いと 403 になる

jobs:
  preview:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: yut0takagi/gas-deploy-action/deploy@v0
        with:
          credentials: ${{ secrets.CLASPRC_JSON }}
          environment: prod
          dry-run: true
          comment-on-pr: true

コメントには隠しマーカー（<!-- gas-deploy-action:<key> -->）を埋め込んでおり、同じキーのコメントは新規作成ではなく更新される。push のたびに積み上がることはない。キーの既定値は複数プロジェクトモードでは environment、単一プロジェクトモードでは default である。

06rollback アクション

ロールバックはデプロイが指すバージョン番号を差し替えるだけの操作である。HEAD のソースは戻らないため、リポジトリ側を revert しなければ次のデプロイで静かに巻き戻る。

ファイルの書き込みもバージョンの作成も行わない。バージョンは Apps Script 側に永続する（削除する API が存在しない）ため、過去のバージョンはいつでも指し直せる。URL も変わらない。

デプロイ直後のロールバックでは version-number を明示する

version-number を省略した「1つ前に戻す」は、現在のバージョンを API から読んで計算する。ところが Apps Script API のデプロイ読み取りは書き込み直後の一貫性を保証しない。実測では deployments.list が30秒以上にわたり古い値を返し続け、しかも新旧の値の間で振動した。

緩和策として、現在のバージョンを一覧ではなく単体取得（deployments.get、実測でより速く収束する）から読み、さらに連続2回の読み取りが一致するまで待つ。一致しなければ推測せず失敗して明示を促す。ただしこれは確率を下げるだけで保証ではない（2回とも同じ古いレプリカに当たると通ってしまう事象を実測で観測した）。

確実な受け渡しには deploy の previous-version-number を使う。デプロイを更新する前に読み取った値なので、この問題の影響を受けない。

- id: deploy
  uses: yut0takagi/gas-deploy-action/deploy@v0
  with:
    credentials: ${{ secrets.CLASPRC_JSON }}
    script-id: ${{ secrets.GAS_SCRIPT_ID }}
    deployment-id: ${{ secrets.GAS_DEPLOYMENT_ID }}

- name: スモークテスト
  id: smoke
  continue-on-error: true
  run: ./scripts/smoke-test.sh

- name: 失敗したら直前のバージョンに戻す
  if: steps.smoke.outcome == 'failure'
  uses: yut0takagi/gas-deploy-action/rollback@v0
  with:
    credentials: ${{ secrets.CLASPRC_JSON }}
    script-id: ${{ secrets.GAS_SCRIPT_ID }}
    deployment-id: ${{ secrets.GAS_DEPLOYMENT_ID }}
    version-number: ${{ steps.deploy.outputs.previous-version-number }}

@HEAD デプロイは常に最新のソースを指すため、バージョンを指し直す操作が成立しない。対象から除外し、指定された場合は専用のエラーを返す。deployment-id を省略してバージョン付きデプロイが複数ある場合は、当てずっぽうに選ばず候補を列挙して停止する。

07事故が起きやすい箇所

この Action の制限事項は「気をつけて使う」で済むものではなく、設定を1つ書き忘れると本番が静かに壊れる類のものである。運用側の対策まで含めて把握する必要がある。

サービスアカウントは使えない。Apps Script API が Google 側の仕様として受け付けない。clasp v3 の --adc オプションも公式に EXPERIMENTAL / NOT WORKING とされている。これは本 Action の制約ではなく Google 側の制約である。

08.claspignore の解釈

.claspignore は glob マッチであり gitignore の意味論を持たない。gitignore の感覚で書いたパターンは、エラーにも警告にもならず静かに何も除外しない。

テストを除外したつもりで実際には本番にテストコードがデプロイされ続ける、という事故を起こしうる箇所である。この挙動は実測で確認し、clasp v3.3.0 自身の判定に合わせてあるため、本 Action 側で「直感的に」修正することはしない。

09品質保証の現状

clasp 互換を自前で保証するリスクは、実際の clasp の判定と突き合わせるゴールデンテストで潰している。実 GAS への E2E も週次ワークフローとして整備した。残る穴は、その E2E に必要な Secrets がまだ設定されておらず、一度も実行されていないことである。

表11: テスト戦略5レベルと実施状況
レベル内容実行頻度状況
1. core 単体file-collector・differ・config・エラー分類常時実施済み

CI は 型検査・テスト・ビルド・dist 同期・バンドル起動の5ゲートで構成する。最後のゲートは実際に3つのバンドルを node で起動し、我々のエラー処理まで到達しているか（::error:: が出るか、かつ SyntaxError 等が出ないか）で判定する。特定のメッセージ文字列で判定していないのは、入力仕様が変わるたびに壊れるのを避けるためである。

E2E は pull_request では意図的に起動しない。Secrets を要するため、フォークからの PR で走らせるとすべて失敗し、外部コントリビュータの PR が理由もなく赤くなる。週次と手動のみとし、さらに Secrets が未設定なら実行せず、「実行しなかった」ことをジョブサマリに明記する（黙って緑にすると、動いていないのに動いているつもりになる）。

この起動ゲートは実際の障害から生まれている。CJS バンドルを .js のまま置くと package.json の "type": "module" により ESM と解釈され、型検査・テスト・dist 同期をすべて通過したうえで本番だけが壊れた。現在は両アクションともエントリを dist/index.cjs にしている。

実 API に対する検証（.claspignore の解釈、デプロイ上限20、スコープ2つでの全操作成功、Web アプリ URL の維持、PR コメントの作成・更新・キー分離、ロールバックの読み取り一貫性）は都度スクリプトで実施し、結果を docs/superpowers/notes/2026-08-09-api-verification.md に記録している。runs.using: node24 も実ランナーで動作確認済み（2026-08-09）。
